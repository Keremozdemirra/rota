## What it claims to do (from its description and topics only)

The description calls it "the black box for AI-written code": a passive
decision graph that links every git commit to the agent prompts that
produced it. Around that core it lists drift detection, a "DLP audit of
what agents read", evidence-driven risk scoring, "MCP memory for coding
agents", and signed provenance attestations. It says it runs as one
command and is offline by default. The topics add `attestation`, `audit`,
`dlp`, `git`, `code-review` and `cli`.

Read together, that is a local tool that records, per commit, which
prompt and which agent session produced the change, and can sign that
record. The words that matter are "passive" and "offline by default":
if both are true, it observes and does not act.

Two of the listed features are a different animal from the rest. "MCP
memory for coding agents" is a memory layer, and "DLP audit of what agents
read" implies it watches file reads, not only commits. Neither is
described further in the metadata.

Nothing here has been cloned, read or run. Everything above is metadata.

## What would have to be true for it to be worth installing

- **Passive must mean passive.** The proposal rests on it recording and
  never injecting, blocking or rewriting. If the "MCP memory" half feeds
  anything back into a session, that half is the `auto-injected memory`
  category in `vetting.yaml` `declined`, and it must be possible to leave
  it off. `thedotmack/claude-mem` was declined for per-tool-call capture
  with no review gate; the same test applies to whatever this reads.
- **Offline must mean no egress at all.** A provenance tool that signs
  attestations may want a key service or a timestamp authority. Any
  outbound connection, even for that, is a question to answer before
  the first run, not after.
- **The graph must be readable without the tool.** Provenance that lives
  in a proprietary store is provenance that disappears with the tool.
  The record has to be plain files in the repository or next to it.
- **It must earn its place against a git trailer.** The `Co-Authored-By`
  trailer already links commits to a model. If the extra value is only
  "which prompt", forty lines in a commit hook may do it without a Rust
  binary that watches file reads.

## Checks a human must run before installing

1. Resolve the install route (the "one command") and the repository
   separately and confirm they fetch the same code, per `tool-vetting`.
   A curl-to-shell installer is a stop until read in full.
2. Find how it observes: a git hook, a Claude Code hook, a filesystem
   watcher, or a wrapper around the agent. A wrapper or a watcher is a
   standing grant and moves this into the runtime-interceptor category
   the SkillSpector proposal set aside.
3. Run it once in a scratch repository with the network watched and
   confirm zero outbound connections, including at attestation time.
4. Read what the "DLP audit" records and where it writes it. A log of
   every file an agent read is itself sensitive; decide where that log
   is allowed to live.
5. Confirm the "MCP memory" component can be disabled, and that the tool
   is still useful with it off. If not, decline for the memory reason.
6. Check the licence covers the whole tree, not only the CLI: a
   dashboard or a signing service under a different licence is a
   second decision.
