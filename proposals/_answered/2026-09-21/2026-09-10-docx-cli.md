## What it claims to do (from its description and topics only)

A command-line tool that lets an agent read, edit and comment on `.docx`
files while preserving formatting. Topics name `ooxml` and `word`, so the
claim is that it operates on the Office Open XML parts rather than
round-tripping through a lossy text conversion. The comment capability is
the unusual part of the claim: reading and writing a document is common,
writing tracked comments into it is not.

Nothing here has been cloned, read or run. Everything above is metadata.

## Which derived gap it fills

`vetting.yaml` `domains` line 4 is `[pdf, docx, ocr, document-extraction,
table-extraction]`. Of that line, `covered` answers none of it directly:
`spreadsheets` covers xlsx and `slides` covers pptx, which are the two
Office formats that are already handled, and `docx` sits in `domains` with
no incumbent named against it. The `pdf` half of the same line was
addressed by the `SylphxAI/pdf-reader-mcp` proposal of 2026-09-05, so this
is the remaining hole in that domain.

The comparison the setup session has to make is with `iOfficeAI/OfficeCLI`
(30,350 stars, Apache-2.0, pushed 2026-09-07), which also appears in this
census and claims Word, Excel and PowerPoint in one binary. Its extra two
formats fall inside `covered`, so the marginal gain over the incumbents is
the same docx half this proposal is about, delivered as a much larger C#
binary. Reach differs by two orders of magnitude here; fit may not.

## What would have to be true for it to be worth installing

- **A docx job must actually exist.** This is the load-bearing condition,
  and it is a question about the work rather than about the tool. CVs,
  cover letters and any document an employer or client sends back with
  comments are the plausible cases. If everything that matters is already
  authored in Markdown and converted at the end, then `pandoc` (already on
  PATH) closes the loop and this fills nothing.
- **Format fidelity must be demonstrable, not asserted.** The whole value
  of an OOXML-level tool is that a document survives a read-edit-write
  cycle unchanged everywhere the edit did not touch. That is testable in
  one command and should be tested before anything depends on it.
- **The npm package and the repository must be the same code.**
  `tool-vetting` treats these as separate routes for a reason. A
  TypeScript CLI installed by name pulls a dependency tree that nobody has
  read, into an environment that handles a job search and client-adjacent
  material.
- **It must stay a CLI.** A tool invoked explicitly on a named file is a
  tool. If it registers hooks, watches directories, or installs itself
  into the session lifecycle, it becomes standing authority over documents
  it was not pointed at, and that is a different decision.
- **197 stars, 8 forks and 0 open issues describe a small project, and
  nothing more than that.** A tidy issue tracker and a quiet one look
  identical from outside. The relevant question is whether the code is
  small enough to read, which at this size it probably is.

## Checks a human must run before installing

1. Answer the docx-job question first. If there is no document that has to
   arrive as `.docx`, stop here and save the review.
2. Round-trip a real document: read it, make one small edit, write it
   back, then diff the unzipped OOXML parts against the original. Anything
   rewritten outside the edited run is a fidelity failure, whatever the
   rendered output looks like.
3. Resolve the npm package name and the GitHub repository separately, and
   confirm they publish the same code. Read the dependency tree before
   installing, per `tool-vetting`.
4. Read the entry point as an execution path: what it opens, what it
   writes, whether it phones anywhere, and whether it does anything on
   install.
5. Test the comment feature specifically against a document that already
   carries someone else's comments and tracked changes. Losing or
   mangling another party's revision marks is worse than not having the
   feature.
6. Compare against `OfficeCLI` and against the installed `docx` skill
   before installing anything. Three tools that open Word documents is
   two too many, and the incumbent should be named in `covered` whichever
   way this goes.
