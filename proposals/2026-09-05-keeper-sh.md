## What it claims to do (from its own description and topics)

A calendar sync tool and "universal calendar MCP server" that aggregates,
syncs and lets an agent control calendars across Google, Outlook, Office
365, iCloud, CalDAV and plain ICS feeds. Topics: `calendar`,
`calendar-sync`, `google-calendar`, `caldav`, `icloud`, `ics`, `mcp-server`.

## Why this looks like a registry gap

`rota/registry.yaml`'s `scout.gaps` list names `calendar` explicitly, and no
route in the registry currently reaches any calendar. Its breadth (multiple
providers behind one MCP surface, not just Google) is a better fit for
"one calendar capability" than a single-provider tool would be.

## What would have to be true for it to be worth installing

- **Licence friction, not a blocker but a fact to weigh:** AGPL-3.0 is
  copyleft — fine to *run* as a standalone server that rota calls over MCP
  (that's normal MCP usage, not linking/distributing AGPL code into another
  work), but per `~/.claude/CLAUDE.md` §5 ("published coefficient/threshold
  wants a primary source + date") and §6 legal red line, if this repo's code
  were ever vendored or modified and redistributed, AGPL's terms would
  apply — worth a conscious note before installing, not a silent default.
- 155 open issues against 1,276 stars is a high ratio — worth reading
  through for whether they're mostly minor sync-edge-cases or something
  more structural before trusting it with real calendar write access.
- It would need actual credentials to Kerem's calendar provider(s) to be
  useful, which means going through the calendar account's own OAuth flow —
  no credential should be typed or stored in plain text per the credentials
  red line, and scope (read-only vs. write) should be the minimum that
  serves whatever the actual use case turns out to be.

## Checks before installing

1. Read a sample of the 155 open issues to gauge whether they're cosmetic
   or indicate real sync-reliability problems (a calendar tool that
   silently drops or duplicates events is worse than no calendar tool).
2. Decide the actual use case first (e.g. interview scheduling during the
   active job search per `memory/kariyer.md`) — install for a real need,
   not because the wishlist names the category.
3. Confirm the OAuth/credential flow it expects and make sure no token
   ever lands in a repo file, only in whatever secret store rota already
   uses for other credentials.
